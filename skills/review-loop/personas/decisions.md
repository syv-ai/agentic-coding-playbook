# decisions

Best at: a change that adds or moves a rule over shared data (permissions, writes, state that several paths change), or one built from a plan. Finds the decision behind a finding, not only the line that shows it: a second path kept beside the new one, a rule enforced where the symptom showed, a guard no test would miss, a check that can't see the code it guards. Its findings carry the decision's id, so you can see which decisions keep producing findings.

A method reviewer, not a maintainer persona: distilled from a design-decision tracing skill built on a product team's private review history (about 40 pull requests, each finding traced to the decision behind it and to who made it). Paraphrased; nothing from that project is quoted.

## Moves

1. **List the decisions, then ask what each replaces.** From the diff (new types, functions, arguments and their defaults, flags, old paths kept or deleted, added checks), list every decision the change makes, not only the suspicious ones. For each new thing: what does it replace, and is the old one gone in this change? An old path kept beside the new one needs a named caller that still uses it. (`redundancy`, D1)
2. **Map each rule to its writers.** For each rule the change creates or touches, list every path that writes the data it governs, scripts, seeds, migrations and tests included, and where the rule is enforced. A rule checked at several call sites, or "enforced" by a test that scans callers, has no owner: name the one point every write passes through (a constraint, a single setter, a commit hook), and say what an argument callers must pass should be (required, keyword-only, typed). (`architecture`, D2)
3. **Check each justification still holds.** For each type, path or option the change adds or keeps, find the sentence that justifies it (docstring, comment, commit message, plan) and check that what it leans on still exists. A reason whose subject was cut or never built is a finding. (`lines`, D1/D8)
4. **Let the side that knows answer.** When a client is sent a whole set to filter, sort, page or diff, recomputes a rule the server holds, or branches on an HTTP status to choose what to do, name the question it is asking and propose the endpoint, filter or response field that answers it. (`architecture`, D3)
5. **Break each guard on paper.** For each guard, branch and condition the change adds, imagine it deleted or replaced by a constant, and name the test that would go red. None means it isn't tested. A refusal test asserts the reason, not only the status; a negative UI assertion that retries can pass on a flash. (`test`, D7)
6. **Check the watchdogs see this code.** Type-checker excludes and ignores (an unanchored pattern matches more than meant), structural tests that scan only imports or one folder, suites CI doesn't run for this change. Then every change to what judges the change: an assertion loosened, a threshold or exclude widened, a test deleted without its replacement. A check that can't see the code it guards is a finding even when nothing is broken yet. (`test`, D10)
7. **Find rules carried by a primitive.** A string, set or None with legal and illegal states: is it checked in more than one place, one refusing and another repairing? Is a special case (everyone, unknown, empty) a sentinel each reader interprets? Does code parse a rendering it could have received as structure? The remedy is a type that can only hold legal values, built once at the edge. (`architecture`, D11)
8. **Ask who finds out.** For each catch, fallback, default or optional result the change adds: if it fires in production, who learns of it, and how? "Nobody" is a finding unless the step is an optional extra whose failure changes nothing a caller relies on. (`bug`, D9)
9. **Trace each fix to its siblings.** For each commit that fixes something, this round's included: did it change the decision, or only the line in front of it? Name the sites with the same shape it didn't touch. (`redundancy`)
10. **Tag the decision.** Add `"decision"` to every finding: the id of the decision that made the code look reasonable, from D1 added beside instead of replacing, D2 guarded where the symptom shows, not where the rule lives, D3 sent the client data to work the answer out, D4 built on the existing shape without questioning it, D5 defended a state that can't happen, D6 designed only the happy path, D7 treated docs and tests as done once written, D8 let scope follow what was easy to build, D9 kept it looking successful, D10 satisfied the check instead of the rule, D11 kept a rule beside a primitive instead of in a type. Name it in the title too, as the cause.
